# Opt-in network library candidate — local review only

This launcher candidate reads `.allium/state/network-library/config.json` and a previously validated `catalog.json` at startup. No configuration means no virtual library, worker, downloads or launcher behavior change. It never discovers or republishes a real NAS catalog automatically. Only an anchored, confirmed absent profile selects legacy launch behavior. Profile/catalog/binding/managed-index/unload-intent startup errors retain a blocked configured PS namespace, show a friendly error modal and log the diagnostic. B closes the modal so Apps/Settings remain accessible; Play, Context Play, Reset, Recents and manual-disc launch still fail before launch side effects until configuration repair and launcher restart. Unknown metadata stays untouched.

The small source profile is `{"version":1,"library_id":"<matching catalog ID>","address":"<explicit private IPv4>:<port>"}`. The endpoint accepts fixed ID routes from the reviewed catalog schema, using streamed HTTP with exact length/SHA/ETag and resumable Range/If-Range. No browser, SMB mount, custom launch command, dependency download or credential is introduced. The root binding is cloned across workers and remains failed after an observed root/ancestor replacement. Restart/rebind requires explicit recovery.

Library and search merge persistent cards without placeholder ROM files. A missing game shows a cloud badge. Existing configured art follows `Roms/PS/Imgs/<cache outer basename>.png`, `.hero.png` and `.orbit.png`; M3U outer names lose only the `.m3u` extension, ordinary directory basenames remain complete. Arbitrary optional catalog art overrides are not consumed in this slice. Cached imported titles retain catalog display names and their original game/launch identity.

Play, context Play, Reset and recent-game Play run through one cancellable background worker. The UI thread alone changes the database, play count, GameInfo and Exec. Every registered CUE track and every disc is cached and freshly SHA-verified before a continuation. Raw registered member paths are normalized back to the logical catalog identity and cannot bypass the bundle guard. Multi-disc selection follows complete verification; confirming a disc rechecks the whole bundle before the existing shared-playlist/.ldci path. Cancellation clears pending launch/disc actions, advances a UI epoch and discards late worker completion; it never starts an emulator. One job/channel is owned until joined before another begins. The daemon's existing hardware resume route is unchanged; the current GameInfo path and any registered member it resumes protect the entire game from unload. This does not add a daemon-side network recovery worker.

Downloading shows streamed byte progress and B cancels. A storage failure offers Manage storage. Manage storage is also available from a network game's context menu: Up/Down select, X toggles largest/least-recently-played sorting, A opens a separate unload confirmation, B returns. Candidate order has stable ID ties. There is no automatic eviction or retry/autoplay after unload. Existing matching payload requires explicit Verify and register confirmation before it becomes managed.

After valid response headers, the first payload byte may take up to 120 seconds while the source prepares it. Later body gaps, including the final close, still time out after 10 seconds. B remains responsive during either wait, and a timeout does not retry automatically; choose Download again only after checking the source is available.

The worker uses actual statvfs allocation accounting and keeps 2 GiB plus a metadata margin. A preexisting `/tmp/stay_awake` is borrowed without being removed; only a worker-created lease is released. Active I/O wakes the launcher at about 33 ms; idle cadence stays unchanged. This is software rendering and a host layout proof, not a hardware FPS claim.

Unload hashes all existing registered payload, rejects unexpected files/directories, protects current resume, and writes a durable intent containing the original file/directory identities. The intent blocks Ready even if the old index still exists. An interrupted removal resumes only after explicit Unload, with remaining inode/SHA checks; absent already-removed members are permitted. Exact committed/scratch intent can recover; unknown/torn metadata and changed/replaced payload remain untouched. Only registered payload, its empty known directories and app-owned cache journal/index/intent are removed. Artwork, cards/catalog, Saves, BIOS, Guides, ratings, bookmarks, history, unrelated files and source archives remain.

Filesystem policy: one managed writer under a process lock, with anchored descriptors, parent validation and no-replace installation. The user-confirmed unload interval requires cooperating external editors to leave registered ROM paths alone. Observed replacements or unknown contents fail closed. Linux/VFAT cannot provide an atomic inode-conditional unlink: an external name swap inside the final validation-to-unlink interval is unsupported. App-owned metadata/staging has the previously reviewed sole-writer policy; no conditional-overwrite atomicity is claimed. Removal runs to the end of its small registered set once deletion starts; B cancellation is honored during the potentially large verification phase. A crash leaves a non-Ready durable intent for explicit recovery.

The reviewed `reset_failed_payload` backend API is retained for an explicit known bad-SHA reset; this slice reports the failure and does not add a UI reset/retry button. Updating the on-device catalog/profile remains an explicit reviewed provisioning step, not a background catalog synchronizer.

Local fixtures use tiny fake bytes only. No real catalog, source ROM, NAS, Downloads, card, device or LAN endpoint was written or published. ARM compile, network reliability and launch/resume on the physical device are still gated on root/independent review and a separately authorized deployment. The approved launcher ELF is retained unchanged for rollback.
